## How to read the assessment

ATT&CK mapping describes observed or assessed adversary behaviour. A submitted command can fit a technique even when there is no proof that the server executed it. Technique identification is therefore separate from success: this document does not establish successful exploitation, webshell installation, persistence, collection, credential theft, stored-data manipulation, container startup or escape.

- **Observed attempt:** The request or command submission explicitly describes the attempted action. Execution and results remain unverified unless separately evidenced.
- **Tentative:** The technique interpretation depends on purpose, deployment state or execution context that is not fully established. This is an assessment, not an observed successful action.
- **Not established:** The evidence does not support the asserted outcome or an additional technique assignment. This does not prove the action never occurred.
- **Confidence:** High means explicit command semantics closely fit the mapping; Moderate means the fit is meaningful but depends on context or an indirect packet association; Low means a hypothesis with little supporting sequence evidence. Confidence applies to the stated assessment, not to successful execution.

## Evidence that would materially change the assessment

1. **Exploitation and deployment:** The full triggering request, authentication/authorization state, exploit-specific server effects, TeamCity audit logs, stored archive/JSP and installation/activation records would distinguish version disclosure, an exploit sequence and component deployment.
2. **Execution and collection:** Correlated process records, exit status and matched response bodies could establish command execution. Returned `ls` output would support a completed listing; returned `/tmp/Creds.txt` contents would support collection and allow assessment of whether credentials were actually present. Preserve redactions when documenting any returned secrets.
3. **File-write purpose and result:** Relevant before/after contents, the file's operational role, write status and subsequent readback would clarify whether anything was changed and why. The earlier read cannot verify the later write, and a successful write alone would not establish an impact objective.
4. **Container and host access:** Docker create/start events, container identifiers, effective privilege and mount settings, daemon identity, initial namespaces/privileges and host-specific access evidence would distinguish deployment attempts, privileged operation and actual escape. Keep the two Docker requests separate.
5. **Packet linkage:** Establish missing streams for 25572, 26895 and 31123 and independently verify 32111's frame-to-body association. Frames 31124/32003 are client requests, not confirming responses. Explicitly pair response bodies with requests before assigning outcomes.
