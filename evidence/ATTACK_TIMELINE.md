# JetBrains TeamCity Attack Timeline — Preliminary

## Basis and limits

This preliminary timeline combines the supplied observations with the [technical evidence register](TECHNICAL_EVIDENCE_REGISTER.md), read alongside the [preservation notes](PRESERVATION_NOTES.md). Evidence IDs refer to the existing [70-screenshot manifest](SCREENSHOT_MANIFEST.csv). Screenshot hashes identify preserved files; they do not establish successful execution, compromise, or authenticity.

**Observation** below means directly visible material as reported by the prior visual audit and inherited through the register, except for the targeted screenshot verification of the frame/Time associations in **EV-008 and EV-014** documented below. Only those two screenshots were re-inspected; no source packets were independently inspected. **Interpretation** describes the apparent purpose of that material, not a verified outcome.

All seven rows increase in both frame number and recorded numeric Wireshark Time. The first two Time values are transcribed directly from EV-008 and EV-014; the other five remain exactly as supplied and inherited from the register. The visible decimal format is consistent with relative seconds, but this interpretation is provisional: neither inspected screenshot exposes the selected time-display mode or zero/reference point. The column records the observed numbers without asserting seconds since capture start or an absolute timestamp basis. No absolute timestamps are calculated. Screenshot filename dates, filesystem timestamps and server-supplied HTTP Date headers are not substitutes for that basis.

**Confidence:** High applies to clearly reported text or identifiers in the inherited audit and to the directly checked frame/Time pairs in EV-008 and EV-014. Moderate applies to associations derived from a filtered packet list or stream footer and to the provisional relative-seconds interpretation. Neither level establishes execution or compromise; the configured time mode, reference point and unsupported outcomes remain unverified.

- **EV-008 — `Screenshot From 2026-11-03 01-41-04.png`:** The selected packet-list row visibly pairs **No. 24711** with **Time 1054.290142**. The packet-details heading also identifies Frame 24711, and the Follow HTTP Stream footer identifies Packet 24711 in stream 364. The numeric Time agrees exactly with register entry 1.
- **EV-014 — `Screenshot From 2026-11-03 02-10-16.png`:** The selected packet-list row visibly pairs **No. 24825** with **Time 1071.315015**. The packet-details heading also identifies Frame 24825, and the Follow HTTP Stream footer identifies Packet 24825 in stream 364. The numeric Time agrees exactly with register entry 2. This screenshot's packet list is displayed in descending frame/time order; the timeline uses ascending order.
- **What is confirmed:** Both numbers are displayed under Wireshark's **Time** column beside the specified packet numbers. They are not screenshot dates or values taken from HTTP headers. Both views identify `Capture.pcap`. Confidence in the two numeric transcriptions and frame associations is **High**.
- **What is not confirmed:** Neither screenshot shows an open **Time Display Format** menu, column configuration, or expanded frame timing fields establishing the selected mode/reference. Decimal values with six fractional digits and the surrounding packet values support a **provisional relative-seconds interpretation (Moderate confidence)**. They do not establish the exact time mode, capture-start offset, reference-packet setting, epoch basis, timezone or absolute event time. The numeric discrepancy is resolved; relative versus absolute classification is not independently confirmed by visible configuration.
- **Preservation and scope:** The two inspected files were located through their manifest IDs and their SHA-256 hashes matched the manifest. Inspection used byte-identical temporary copies read from the originals without access-time updates. No other screenshots were inspected. The register's numeric entries required no correction; the remaining five event rows and their findings were retained unchanged.

## Evidence gaps and unresolved questions

1. **Numeric discrepancy resolved; time mode unverified:** EV-008 and EV-014 visibly confirm `1054.290142` for frame 24711 and `1071.315015` for frame 24825, matching the register. The previous Unknown cells are replaced with those exact observed values. Confirm the Wireshark time-display mode and reference point before treating their provisional relative-seconds interpretation as established or making absolute-time conversions.
2. **Capture and clock basis:** Establish the source capture, packet timestamp origin, Wireshark Time column settings and any timezone/clock assumptions before assigning absolute times. Independently validate frame numbers, reassembly and ordering. These selected observations do not establish the complete attack sequence.
3. **Version and upload outcomes:** What request triggered the version response? Was an exploit successful? Was the archive accepted, installed or activated? A version string and later requests to a matching JSP path cannot answer these questions alone.
4. **Command and credential outcomes:** Obtain matched responses, command output or server-side artifacts establishing execution. The documented read request precedes the documented write request; it cannot verify that later write. Earlier file creation, existing contents, write success, subsequent readback and credential use remain unknown.
5. **Stream and response mappings:** Stream IDs remain unestablished for frames 25572, 26895 and 31123. Frames **31124** and **32003** are client POSTs, not server responses; their bodies and stream IDs require review. Nearby HTTP 200 response rows **32008/32010** lack verified request pairing and inspected bodies.
6. **Docker outcomes and frame selection:** Keep frame 32002's privileged-container request separate from packet 32111's bind-mount/chroot request. EV-069 repeats EV-068's request rather than adding an event. EV-070's background selection **32010** must not replace footer reference **32111**. The HTTP 200 response following the mount/chroot body advertises four response bytes, but no readable output or response frame ID is visible. Confirm packet-to-body/response linkage, Docker execution and actual host access before claiming compromise.

This timeline is preliminary. No successful command execution, credential compromise, container escape or host compromise is established by these observations. The technical evidence register, screenshot manifest, preservation notes and original screenshots were left unchanged.
